Capítulo 1 • Information Retrieval

Achar o trecho certo antes de o LLM abrir a boca

Information Retrieval resolve um problema simples de descrever e difícil de fazer bem: dado um monte de documentos e uma pergunta (query), encontrar rapidamente os documentos mais relevantes — sem ler tudo do zero a cada busca.

Pense no Google, num Ctrl+F inteligente, ou na busca do seu e-mail. Todos fazem a mesma coisa: recebem uma query e devolvem uma lista ordenada por relevância. RI é a teoria e as técnicas por trás disso.

As 3 peças de todo sistema de RI

Indexação

Pré-processa os documentos numa estrutura rápida de consultar — não varre tudo linearmente a cada busca.

índice invertido · índice vetorial

Ranking / Score

Mede o quão relevante cada documento é para a query. É aqui que mora a diferença entre as técnicas.

BM25 · similaridade de cosseno

Recuperação

Devolve os top-K documentos mais bem pontuados — o que efetivamente chega na próxima etapa.

top-5 chunks mais parecidos

Léxica / esparsa

Compara palavras literalmente. Rápida, explicável, ótima quando a palavra certa importa — nomes próprios, códigos, jargão técnico. TF-IDF, BM25.

Semântica / densa

Transforma texto em vetores (embeddings) e compara por significado, não por palavra exata. Acha “aumento de temperatura corporal” quando a query é “febre”. Busca vetorial: FAISS, pgvector, kNN do Elasticsearch.

Na prática, sistemas bons combinam as duas (hybrid search): a léxica pega o termo exato, a semântica pega o sinônimo. É exatamente onde este capítulo termina.

Por que RI é o coração do RAG

RAG (Retrieval-Augmented Generation) é a técnica de dar a um LLM acesso a uma base de conhecimento externa antes de ele responder. O nome já entrega a ordem das coisas: primeiro Retrieval, depois Generation.

O LLM nunca vê a base inteira. Ele só vê o que a etapa de RI escolheu entregar. Se a RI errar o que é relevante, o LLM erra a resposta — não importa o quão bom o modelo seja.

Sem RI de qualidade, RAG vira “garbage in, garbage out”

RI fraca → alucinação

Contexto errado gera resposta errada, mesmo que a informação certa exista na base.

RI lenta → RAG lento

A busca acontece a cada pergunta, em tempo real. O custo dela entra em toda resposta.

Ranking ruim → contexto poluído

Manda 10 trechos, só 1 é útil, e o LLM se perde no meio do ruído.

Por que não simplesmente colocar tudo no prompt?

Porque o LLM tem uma janela de contexto limitada e cara (em tokens e em custo), e bases de conhecimento reais — documentação, contratos, tickets, código — são grandes demais para caber inteiras. RI é o filtro que decide, de milhares de páginas, quais poucas realmente importam para essa pergunta específica.

Veja a diferença na prática

Uma base fictícia com 5 trechos de prontuário. Escolha uma pergunta e compare o que a RI léxica (só palavras exatas) recupera contra o que a RI semântica (por significado) recupera — e o efeito disso na resposta final do LLM.

Resumo

RI não é um detalhe de implementação do RAG — é a etapa que determina se o sistema vai funcionar. Um LLM excelente com recuperação ruim continua respondendo mal. Por isso, boa parte do trabalho de construir um RAG confiável está em melhorar a RI: escolher a técnica certa (léxica, semântica ou híbrida), o tamanho certo de chunk e o ranking certo.
